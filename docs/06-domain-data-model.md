# Catsflow 論理データモデル候補

- 更新日：2026-10-16
- 文書状態：論理設計案。物理DBのテーブル名・カラム名・DDLを確定する文書ではない
- 目的：家計簿・資産・負債・投資・長期目標・月次評価を一貫して管理するための概念整理

## 1. 設計原則

1. 既存スキーマを先に調査し、再利用できる構造を優先する。
2. 本書の論理エンティティ名を、そのまま新規テーブル名として実装しない。
3. 取引履歴と残高スナップショットを区別する。
4. 資産と負債を別に管理し、純資産は同じ基準日の値から算出する。
5. インポート元・手動入力・更新日時を追跡する。
6. 過去の月次評価を、後日の目標変更で書き換えない。
7. データがない値と、金額ゼロを区別する。

## 2. 既存スキーマ（提供ZIPで確認）

| テーブル | 現在確認できる用途 | 注意点 |
|---|---|---|
| `users` | ユーザー | 認証方式・パスワード保存運用を確認 |
| `line_user_links` | LINEユーザー紐付け | 連携・解除・再連携のルールを確認 |
| `webhook_events` | Webhookイベント記録 | イベント重複処理の実装と整合させる |
| `sync_logs` | 同期・取り込み履歴 | メッセージ長・個人情報を確認 |
| `accounts` | 口座・カード等 | 資産残高・カード債務をどう表現するかは未確定 |
| `categories` | 取引カテゴリ | カテゴリの親子・収支区分の扱いを確認 |
| `import_files` | CSV取込記録 | 同期ログとの役割分担を確認 |
| `transactions` | 家計簿取引 | 金額符号、振替、投資移動、返済の区分を要確認 |

提供ZIPの `schema.sql` では、以下の領域専用のテーブルは確認できない：
- 資産残高の基準日履歴
- 負債と返済履歴
- 個別投資商品・保有数量・取得原価・評価価格
- 長期目標と目標変更履歴
- 月次評価と評価時点の数値
- 予算の永続化（別の保存手段がないかはソース調査が必要）

## 3. 論理エンティティ候補

### 3.1 取引（既存 `transactions` を中心に検討）

目的：家計の現金流出入・資金移動・投資取引・返済を履歴として記録する。

候補情報：
- 所有ユーザー
- 取引日
- 金額
- 取引区分
- 説明・カテゴリ
- 口座
- 振替の対応関係（必要な場合）
- 取得元／インポートID
- 手動修正状態・更新日時

未決定：
- 金額の符号規約
- `type` の値と拡張方針
- 振替の片側／両側の保存方法
- 投資商品の売買を家計取引と別管理するか、関連付けるか

### 3.2 資産と残高履歴

目的：預金・現金・投資資産等の基準日時点の価値を保持する。

候補情報：
- 資産の種類・名称
- 金融機関・口座（関連付ける場合）
- 基準日
- 評価額
- 通貨
- 評価方法・取得元
- 最終更新日時

取引履歴から常に残高を完全復元できるとは限らないため、必要に応じて残高スナップショットを保持する。

### 3.3 負債と返済履歴

目的：借入残高と返済状況を把握し、資産形成評価に含める。

候補情報：
- 負債の名称・種類
- 残高と基準日
- 金利（不明値を許容）
- 月次返済額
- 返済日・完済予定日
- 元金・利息の内訳（取得できる場合）
- 繰上返済条件（確認できる場合）
- 返済履歴と取得元

不明な金利・条件は推測で設定しない。

### 3.4 投資積立計画・投資信託資産推移

初期版では、銘柄別の保有数量や評価額ではなく、ユーザーが設定する積立計画とMoneyForward ME資産推移CSV由来の投資信託全体額を管理する。

**投資積立計画（論理概念）**
- ユーザー
- 銘柄名（ユーザー入力。識別コードは初期必須にしない）
- 毎月の投資予定額
- 積立開始月（採用する場合）
- 積立状態（積立中／停止中）
- 作成日時・更新日時

**資産推移スナップショット（論理概念）**
- ユーザー
- 基準日
- 資産総額
- 投資信託カテゴリの資産額（CSVに存在する場合）
- 取得元・取込日時

この記述は論理モデルであり、既存DBに対応テーブルが存在することを意味しない。物理テーブル・カラムは現行スキーマを確認してから設計する。

**初期版対象外**
- 保有数量・口数・取得単価・取得原価
- 銘柄別評価額・評価損益
- 売買・配当・分配金履歴

投資信託全体の資産額を銘柄別に按分してはならない。月額設定は投資計画であり、実際の買付実績とは区別する。

### 3.5 長期目標と履歴

目的：貯金・資産形成・返済などの目標を設定し、進捗を継続管理する。

候補情報：
- 目標名・種類
- 目標金額・期限
- 現在値・進捗
- 月次の積立・返済計画
- 優先度・状態
- 作成日・変更日
- 目標変更履歴

目標を変更した場合も、過去の月次評価に使った目標値を再現できるようにする。

### 3.6 月次評価

目的：同じフォーマット・計算ルールで毎月の実績を保存する。

候補情報：
- 評価対象年月
- 評価作成日時
- 使用した取引・残高の基準日
- 収支・貯蓄実績
- 資産総額・負債総額・純資産
- 投資評価値（取得可能な場合）
- 目標進捗と評価時点の目標値
- データ品質・不足項目
- 計算ルールのバージョン
- AIコメントと、計算値から区別した提案内容

月次評価の数値は可能な限り決定的なプログラム計算とし、AIの文章生成と分離する。

### 3.7 データ出所・同期履歴

目的：どの情報がどこから、いつ取り込まれたかを追跡する。

候補情報：
- 取得元（CSV、手動入力、公式連携等）
- 取り込み日時
- 対象期間／基準日
- 成功・失敗状態
- 件数・エラー概要
- 元データとの関連
- 手動修正の有無

既存の `import_files` と `sync_logs` の責務を調査し、重複した履歴構造を不用意に増やさない。

### 3.8 生活プロフィール（将来候補）

目的：家計の数字だけでは分からない生活背景を、ユーザーの同意・入力に基づいて資産形成評価へ反映する。

候補情報：
- 住居形態（例：実家暮らし・一人暮らし・同居）
- 住居費・生活費の本人負担状況
- 収入の安定性に関する自己申告
- 家族への仕送り等の継続負担
- 今後の予定（引っ越し、転職、大きな買い物等）
- 本人の優先事項
- 作成日時・更新日時（変更履歴を保存するかは未決定）

原則として任意入力とする。未入力は「なし」「0円」を意味しない。ユーザーが登録した事実とAIの推測・解釈を分け、生活環境の変化を必要に応じて更新できる設計とする。健康・家族等の機微情報は必要以上に収集しない。

### 3.9 生活防衛資金の目安（将来候補）

候補情報：対象とする現金・預金、目標額または生活費に対する月数、基準日、設定根拠、現在額との差。目安月数や対象資産の定義は未決定であり、ユーザーが設定・確認できることを想定する。

### 3.10 将来シミュレーション（将来候補）

候補情報：シナリオ名、変更した前提（積立額、返済額、収入・支出、イベント等）、対象期間、計算結果、作成日時。シミュレーションは実績データとは別に保持し、前提条件と不確実性を明示する。

### 3.11 データ変更履歴・評価根拠（将来候補）

候補情報：対象データ、変更前後の値、変更者／変更元、変更日時、変更理由（任意）、参照した月次評価の数値・計算ルール、AIコメント。既存のインポート／同期ログと役割が重ならないよう、実装前に責務を整理する。履歴の保存対象・保持期間は未決定。

## 4. 基本計算ルール候補

- 純資産 = 同一基準日の資産総額 − 負債総額
- 投資信託全体の資産額は、資産推移CSVに記録された基準日時点の値を利用する。
- 初期版では銘柄別評価額・評価損益を計算しない。
- 目標進捗率 = 進捗額 ÷ 目標額（目標額が正で定義済みの場合）
- 完済見込みは金利、返済額、返済条件が確認できる場合のみ計算する。

値が未取得、基準日不一致、計算条件不足の場合は、ゼロや確定値として扱わず状態を記録する。

## 5. 月次評価における二重計上の注意

- 口座間振替：消費支出として二重計上しない。
- 投資口座への入金：資産間の移動として扱い、投資商品の購入と二重計上しない。
- 投資購入：現金から投資資産への移動として扱う。手数料等は別途支出として扱う方針を検討する。
- 元金返済：現金減少と負債減少の両方に反映する。
- 利息：負債残高の減少ではなく、費用として扱う。
- 投資信託全体の資産額の増減：追加投資・売却等を区別できないため、運用損益と断定しない。

## 6. 物理DB設計に進む前の必須確認

1. 既存コードで各テーブルがどう利用されているか
2. 現在のデータと `data.sql` の内容
3. `transactions.amount` の符号と `type` の意味
4. H2の初期化・再起動時のデータ保持要件
5. 既存認証・ユーザー識別方式
6. マネーフォワード MEの実CSV
7. 投資管理の対象商品と取得価格の更新方法
8. 手動修正と再インポートの優先ルール

この確認が終わるまで、ここに書かれた候補を確定DDLとして実装しない。

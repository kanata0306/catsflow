## 1. システム構成

### 現状確認（提供ZIP）

- Java 21、Spring Boot、Spring JDBC、H2
- LINE Webhook、LINEログイン／認証関連のController・Service
- LINEユーザー紐付け、Webhookイベント記録
- 取引集計Service
- CSV取り込みService
- Thymeleafテンプレート
- React + TypeScriptのMini Appフロントエンドは提供ZIP内で確認できない

### 方針

- バックエンド：既存Java / Spring Bootを継続
- 開発用DB：H2
- フロントエンド：LINE Mini App（React + TypeScript）を主画面とする既存方針を維持
- 独立した通常Webサイト：必要性が確認されるまで作らない
- 本番DB・公開先：未決定
- 既存のService／Repository／認証を優先調査し、不要な二重実装を避ける

## 3. 初期LINEコマンド

| コマンド | 目的 | 応答内容 |
|---|---|---|
| `今月` | 当月の家計状況 | 収入・支出・収支。取得可能な項目のみ |
| `予算` | 予算の確認 | 予算額・使用額・残額・使用率。予算データが存在する場合 |
| `カテゴリ別` | カテゴリ別支出 | カテゴリ名と金額 |
| 将来：`資産` | 資産状況 | 最新基準日の資産総額・純資産 |
| 将来：`負債` | 負債状況 | 負債残高・返済進捗 |
| 将来：`目標` | 長期目標 | 目標進捗と次の行動候補 |

共通ルール：
- 前後空白を除去してコマンド判定する。
- 初期コマンドは参照のみ。作成・更新・削除は行わない。
- データ未登録・未取得の項目は推測値を表示しない。
- コマンドの応答内容は、ユーザー本人のデータに限定する。

## 4. 家計簿データの取り扱い

### 4.1 取引区分

論理的に区別したい区分：
- 収入
- 消費支出
- 口座間振替
- 投資商品の購入・売却
- 配当・分配金
- 負債の元金返済
- 利息・手数料
- その他の資金移動

この区分を既存の `transactions.type` にそのまま追加するか、別の区分項目を持たせるかは未決定。現在のスキーマと取り込みコードを確認し、互換性・データ移行方法を決める。

### 4.2 金額・符号規約

提供ZIPの `CsvImportService` は、取り込みコード上で支出額を負数として保存する処理がある。今後は「金額を常に正数で持ち、区分で方向を表す」などの統一案も考えられるが、既存データ・集計ロジックとの整合性を確認せずに変更しない。

決定前に確認すること：
- 現在のH2に入る値と画面表示
- 既存集計Serviceが符号と `type` のどちらを基準にしているか
- CSV上の金額符号・振替表現
- 既存データ移行の必要性

### 4.3 重複計上防止

- 同一CSVや同一明細の再取り込みで重複を作らない。
- 口座間振替は支出・収入の両方を消費として計上しない。
- 投資口座への入金と証券購入を家計支出として二重計上しない。
- 元金返済は現金の減少と負債の減少に反映し、純資産計算で二重に損失扱いしない。
- 元データ・手動修正・取り込み元を識別できるようにする。

## 5. 資産・負債管理

### 5.1 資産

管理候補：
- 現金・預金
- 投資商品
- その他の金融資産
- 評価基準日
- 評価額とデータ取得元
- 最終更新日時

資産総額は基準日時点の各資産の評価額を集計する。資産推移CSVの総額と個別資産データの合計が異なる場合、どちらを正とするかを自動で決めず、差異を検出・表示する方針を検討する。

### 5.2 負債

管理候補：
- 負債名・種類
- 現在残高
- 金利（不明なら未設定）
- 毎月の返済額
- 返済日・完済予定日
- 返済履歴
- 繰上返済条件（確認できる場合）
- データ基準日・出所

残高・金利・条件が不明な場合は推測で補完しない。元金・利息を分けて取得できない場合は、取得できないことを明示する。

### 5.3 純資産

基本式：

`純資産 = 資産総額 - 負債総額`

月次評価では、同じ基準日の資産と負債を用いる。基準日が異なる場合は、比較可能性が低いことを表示する。

## 6. 投資管理（初期版）

### 6.1 目的と確定範囲

初期版では、銘柄ごとの積立計画をCatsflowで管理し、MoneyForward MEの資産推移CSVから投資信託カテゴリ全体の資産額を取り込む。個別銘柄の保有状況を完全に再現することは目的にしない。

Catsflowで管理する項目：
- 投資銘柄名（ユーザー入力）
- 毎月の投資予定額
- 積立開始月（計画の月次集計に必要な場合）
- 積立中／停止中の状態

MoneyForward ME資産推移CSVから取り込む項目：
- CSVに含まれる基準日
- 資産総額
- 「投資信託」カテゴリの金額（実CSVに該当列がある場合）
- 取込元・取込日時

### 6.2 初期版の対象外

- 銘柄ごとの現在評価額・評価損益
- 保有数量・口数・取得単価・取得原価
- 銘柄別の売買履歴、配当・分配金、実現損益
- 資産推移CSVの全体額を銘柄別に按分すること

上記は入力データがないため推定・按分して表示しない。個別銘柄の評価額や損益は「未対応」とし、ゼロや推定値を実績として表示しない。

### 6.3 集計・評価ルール

- 月次の予定投資額は、積立中の銘柄に設定された月額の合計として計算する。
- 予定投資額は計画値であり、実際に買付が行われた証拠とはみなさない。
- 投資信託カテゴリの資産額は、CSVに記録された基準日時点の値として保存する。
- 投資信託全体の資産額の増減を、そのまま運用損益と解釈しない。追加投資・売却等を区別できないため。
- CSVに「投資信託」列がない場合、値を推測せず「取得不可」とする。

### 6.4 将来拡張

個別銘柄の評価額・損益は初期版に含めない。将来拡張する場合は、保有明細を提供する正式な取得経路と、実際に取得可能な項目を確認したうえで別途仕様化する。

## 7. 長期目標・計画

目標の論理情報候補：
- 目標名・目的
- 目標金額
- 目標期限
- 現在の進捗額
- 毎月の積立計画
- 優先順位
- 対象資金（現金、投資、負債返済等）
- 作成日・変更履歴・状態

目標変更時に過去の月次評価を上書きしない。評価時点の目標値を保存するか、履歴を参照できる設計にする。

## 8. 月次評価

### 8.1 出力構成（確定方針）

1. 家計収支
2. 貯蓄実績
3. 資産・負債・純資産の推移
4. 投資積立計画と投資信託全体の資産推移
5. 目標進捗
6. 前月・計画との差異
7. データ品質と不足情報
8. 総合評価と根拠
9. 翌月の具体的な行動候補

### 8.2 指標を混ぜない

- 家計収支と純資産の変化を別指標にする。
- 投資信託全体の資産額の増加を運用利益と断定せず、給与等からの貯蓄と混同しない。
- 元金返済による負債減少と現金減少を両面から反映する。
- 資産総額の増加をすべて投資成果と解釈しない。
- データの欠損や基準日差異を評価に織り込む。

### 8.3 AI支援（後続）

AIへの入力候補：
- 期間・基準日
- 確定した計算値
- 過去の目標・評価
- 未取得データと注意事項

AIの出力候補：
- 状況の要約
- 計画との差異と根拠
- 複数の選択肢とトレードオフ
- 翌月に実行する具体的な行動候補

AIは未取得値を事実として補完しない。金融データの更新や目標変更はユーザー承認を必要とする方針を推奨する。

## 9. 手動登録・修正とインポートの競合

仮決定：
- 取引・資産・負債・投資保有情報にはデータ出所と更新日時を保持する。
- ユーザーが手動修正した値を再インポートが無条件に上書きしない。
- 元データを保持するか、変更履歴を保持するかは個人情報・保守負担を含めて決定する。
- 競合時は自動上書きせず、差分表示・ユーザー選択などの方式を検討する。

## 10. 追加予定機能の概要

以下は将来候補の論理仕様であり、現時点で画面・API・DBが実装済みという意味ではない。物理DB設計は既存スキーマを確認してから行う。

### 10.1 純資産・資産構成の可視化
- 同じ基準日の資産総額・負債総額から純資産を算出する。
- 資産種別や負債種別の構成・時系列を表示する。
- データの基準日が一致しない場合は注意を表示し、単純比較の確度を下げる。

### 10.2 長期目標・達成予測
- 目標金額・期限・目的・優先度を管理する。
- 現在の進捗と必要な月次積立額を試算する。
- 利回り等の仮定を置く場合は実績と区別し、仮定を明示する。投資成果を保証する表示は行わない。
- 目標変更の前後を追跡し、過去の月次評価を後から書き換えない。

### 10.3 月次レビュー・改善履歴
- 毎月、家計収支・貯蓄・資産・負債・純資産・投資計画・目標進捗・データ品質を同じ構成で評価する。
- 評価時点の数値、適用目標、計算ルール、AIコメント、翌月の行動候補を保存する案とする。
- 既存の `sync_logs` 等は取り込み運用ログであり、月次評価履歴の代用と決めつけない。

### 10.4 生活防衛資金管理
- 現金・預金等のうち生活防衛資金として扱う範囲を定義する。
- 目安額は生活費・収入安定性などを踏まえて設定可能にする案とする。
- 目安の算定月数・対象支出・現金として数える資産は未決定。AIが一律の値を事実として決めない。

### 10.5 生活プロフィール
- 将来候補の項目：住居形態、住居費・生活費の本人負担、収入の安定性、家族への仕送り等、今後の予定、本人の優先事項。
- 入力は原則任意とし、未入力をゼロや「負担なし」と解釈しない。
- 登録された事実とAIの解釈を分ける。プロフィール変更履歴は、必要性・プライバシー・保存期間を検討してから実装する。

### 10.6 将来シミュレーション
- 積立額変更、返済優先、転居、収入減少、臨時出費などの条件を変え、結果を比較する。
- 試算は前提条件・対象期間・不確実性を表示し、確定した将来予測として扱わない。
- シミュレーション値は実績データを上書きしない。

### 10.7 LINE通知・定期レポート
- 月次レビューの案内、目標進捗、予算超過などを通知候補とする。
- 通知の種類・頻度・静音時間・停止設定・再送制御は未決定。
- LINE通知の送信対象は連携済みユーザーに限定し、通知内容に不要な個人情報を含めない。

### 10.8 データ訂正・変更履歴
- CSV取り込み、手動修正、目標変更、生活プロフィール変更の出所・更新日時・変更内容を追跡する案とする。
- 既存の `import_files`・`sync_logs`・`webhook_events` の責務を調査し、履歴機能を重複実装しない。
- 履歴保存の対象・保持期間・復元機能・ユーザー表示は未決定。

### 10.9 AI評価の根拠・データ充足度表示
- AIの評価コメントには参照した計算値と期間を関連付ける。
- 実績値、ユーザー入力、プログラム計算、将来試算、AIによる解釈を区別する。
- 未取得項目や基準日のずれがある場合は、その制約を表示する。
- 「信頼度」の数値化を行うかは未決定。根拠のない確率・スコアを表示しない。

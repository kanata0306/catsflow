## 2. 取引集計の挙動（確認結果）

### 2.1 金額の符号規約 → U-003を確定できる

**事実：**
- 取り込み時（[CsvImportService.java](../src/main/java/com/catsflow/catsflow/Service/CsvImportService.java)）：金額が0以上なら`income`で正数、負なら`expense`で絶対値を負数化して保存
- 集計時（[TransactionSummaryService.java](../src/main/java/com/catsflow/catsflow/Service/TransactionSummaryService.java)）：`type`で収支を判定し、金額は絶対値（`abs()`）で合計
- サンプルデータ（[data.sql](../src/main/resources/data.sql)）：支出は負数で保存（例：`-3500`）

**結論：** 符号規約は「支出=負数、収入=正数」で一貫しており、集計との整合性は取れている。**U-003は「支出を負数で保存する規約」として確定可能**。

**残課題：** MF CSVの「計算対象」「振替」列が未処理のため、振替明細が支出として二重計上される可能性がある（06の5「二重計上の注意」に未対応）。

### 2.2 集計の方式

- `TransactionSummaryService`は当月データを全件取得し、Java側でループ集計している
- SQLで`SUM`+`GROUP BY`による集計に置き換え可能（データ量が増えた場合の効率化候補）
- `TransactionRepository.findThisMonthByUserId`はカテゴリ名をLEFT JOINで取得済み

## 3. CSV取り込みの挙動（確認結果）

### 3.1 実装済み

- ファイル名・拡張子・空内容の検証
- ヘッダーによる種別判定：`日付`+`内容`+`金額` → `transactions`、`日付`+`合計` → `assets`
- 必須列検証（種別ごとに定義）
- クォート・改行コード（CRLF/LF）対応のCSVパーサー
- 取り込み履歴（`import_files`）と同期ログ（`sync_logs`）への記録
- カテゴリの自動作成（大項目→中項目→未分類の優先順）
- 取り込み先口座はユーザーの先頭口座を使用

### 3.2 未実装・問題点

| 問題 | 影響 | 対応方針 |
|---|---|---|
| 重複排除がない | 同一CSV再送で二重登録（受け入れ条件違反） | MFの「ID」列を外部キーとして照合。IDがない場合の複合キーは実CSV確認後に設計 |
| 「計算対象」列を無視 | 計算対象外の明細も集計に含まれる可能性 | 実CSVで列の有無と値を確認後に対応 |
| 「振替」列を無視 | 口座間振替が支出として二重計上される | 06の5に基づき振替を区別して保存 |
| 資産推移CSVの保存処理がない | `assets`と判定されても何も保存されない | 資産スナップショットの物理設計後に実装 |
| 文字コード未対応 | 入力がString前提のため、Shift-JISの実CSVは文字化けの可能性 | バイト列で受け取り文字コード検出する層の追加が必要 |
| 日付形式がISO固定 | `LocalDate.parse(..., ISO_LOCAL_DATE)`のため`yyyy/MM/dd`形式は失敗 | 実CSVの日付形式確認後に対応 |

### 3.3 取り込み入口

- 現在、CSV取り込みを呼び出すHTTPエンドポイントが存在しない
- Webhookはテキストメッセージのみ処理し、ファイルメッセージは未対応
- Mini Appからのアップロード用エンドポイントも未実装
- **02の4.1.1「Mini Appアップロード主経路」の実装が必要**

## 4. 認証・連携の挙動（確認結果）

### 4.1 実装済み

- LINE IDトークンをサーバー側でLINE API（`/oauth2/v2.1/verify`）に検証
- `aud`（チャネルID）と`sub`（ユーザーID）の検証
- クライアント送信のLINEユーザーIDだけでは連携判定しない（設計書の必須ルールに合致）
- メールアドレス正規化（小文字・trim）、パスワードポリシー（12文字以上・72バイト以内、BCrypt）
- 別アカウントへの意図しない上書き防止（`IllegalStateException`）
- 新規登録時にデフォルト口座（現金）を自動作成
- 連携解除（`unlink`）で紐付けレコード削除

### 4.2 注意点

- 連携コード（一時・一回限り）の仕組みは未実装。現在はMini App内でIDトークン検証＋ログイン/登録で直接連携する方式
- 02の「一時連携コードまたは検証済みトークンを受け取り」の「検証済みトークン」方式に相当すると解釈できるが、設計書との用語の整合は要確認

## 5. DBスキーマの現状

### 5.1 存在するテーブル

`users`、`line_user_links`、`sync_logs`、`webhook_events`、`accounts`、`categories`、`import_files`、`transactions`

### 5.2 存在しないテーブル（06と照合）

- 資産残高の基準日履歴 → **資産推移CSV保存に必要**
- 負債と返済履歴
- 投資積立計画
- 長期目標と目標変更履歴
- 月次評価
- 予算 → **U-005：予算コマンド実装に必要**

### 5.3 その他の確認

- H2はインメモリ（`jdbc:h2:mem:testdb`）で、再起動時にデータ消失。開発中のデータ保持要件の確認が必要
- `Entity/Transaction.java`はDBスキーマと不整合（`date`が`LocalDateTime`、`amount`が`int`）。実際には未使用で、`TransactionRepository`はJdbcTemplateで直接操作
